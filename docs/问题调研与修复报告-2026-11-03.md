## 二、问题 1：切到第三方模型后团队仍不可用

### 问题表现

用户将 Lead 模型从官方套餐（`account:bigmodel-individual-coding-plan/GLM-5.3`）切换到自配第三方模型（`new-provider/doubao-seed-2.1-lite`）后，团队功能仍然不可用，提示「spawn_teammate 会失败」。

### 复现逻辑

1. 新建会话，使用官方套餐模型
2. SessionStart hook 注入降级提示：「Teammates unavailable in this session: the Lead's model is an official plan model that teammate processes cannot inherit, so spawn_teammate will fail. Do all work yourself in this session and do not call spawn_teammate」
3. 用户切换到第三方模型
4. 模型仍然拒绝调用 `spawn_teammate`，理由是「官方套餐模型无法继承」

### 根因

`DEGRADED_SOLO_NOTE` 使用了**禁止性祈使句**（`do not call spawn_teammate`），该句进入对话历史后**不可撤销**。即使后续注入撤回提示（`SOLO_RETRACT_NOTE`），模型仍服从早期禁令，全程不尝试 spawn。

**关键证据**（sess_059af35f）：
- `soloRetractedAt` 已落盘（撤回提示已注入）
- 但 `tool_usage` 只有 `Bash`，**0 次 `spawn_teammate`**
- 模型 reasoning：「the system says teammate processes can't inherit this model... I should not call spawn_teammate」

### 修复

**D30 修订（0.5.3）**：
- 提示改为**纯事实描述**：「此刻调用会因继承限制失败；一旦换成自配第三方模型就正常可用，无需额外确认」
- **禁止任何禁止性祈使句**（`scripts/text-audit.mjs` 加反向断言：`do not call` / `must not` / `never call` 一律禁止）
- 撤回提示显式声明早前提示失效，并要求**用一行告知用户「队友已可用」**（此前模型心里知道但不告知，用户感知不到恢复）

### 验证

- sess_e6a3526d：模型 reasoning 明确「the earlier notice has been voided, and the teammate spawning function is now working normally」
- sess_cabd748c：切回套餐后 UPS 对账注入事实版提示，Lead 一行说明+自干+交付

### 关联 Issue

- GitHub Issue #5（订阅套餐模型不可继承，降级自干）

## 三、问题 2：`/team <任务>` 只输出状态摘要，不真正建队

### 问题表现

用户输入 `/team 把这段故事扩写成三个角色`，期望团队执行，但只得到状态摘要（「成员 1 · 共享任务 0」），然后模型自己写故事，没有建队。

### 复现逻辑

1. 用户输入 `/team <任务>`
2. 命令规范（`commands/team.md`）明确「本命令**只读**：不创建/修改/删除任务或成员」
3. 模型只读状态，然后自行代劳

### 根因

`/team` 命令的设计缺陷：**带参数时应该建队执行，但规范写成只读**。

### 修复

**0.5.3 修订**：
- `/team`（无参）= **只读**状态摘要与面板入口
- `/team <任务>`（带参）= **直接建队执行，不输出状态摘要**（b51ff30 追加：去掉摘要输出，用户要的是团队干活，不是看状态）

### 验证

- sess_cabd748c：`/team` 带参建队 5 成员 3 任务三工序流水线交付（架构师→执笔→编辑）
- 工具调用：`spawn_teammate` ×5、`team_task_create` ×3、`wait_agent` ×14

### 关联 Issue

- 无独立 issue（0.5.3 直接修复）

## 四、问题 3：创建成员时报错

### 问题表现

创建成员时面板出现红字：
- `provisioning did not leave a resumable child Session`
- `app-server rpc timeout: v4/command`

### 复现逻辑

**场景 A（provisioning did not leave）**：
1. Lead spawn 成员，provisioning 事件落盘
2. 协调者锁被抢（心跳过期）
3. 新协调者构造即跑 `reconcileProvisioning`
4. 此时 origin.json 还没写（createChild 需要 7–46s）
5. `readProvisioningRecord` 返回 undefined → 判 failed

**场景 B（app-server rpc timeout）**：
1. session-breeder 调用 `v4/command`（anchor `createSession`、`createSelectionSideSession`）
2. RPC 30s 超时即抛错，无重试
3. `anchorSessionId` 未捕获 → 无法 tombstone，可能泄漏到侧边栏

### 根因

**场景 A**：
- 协调者锁心跳是 1s 同步写盘，daemon 事件循环被同步 fsync 卡住时心跳文件停滞 >4.5s 过期阈值 → 活着的持有者被判死亡、锁被抢
- 新协调者上任瞬间跑 reconcile，in-flight spawn 的 origin.json 还没落盘 → 误杀

**场景 B**：
- `app-server-client.mjs:145-152`：RPC 单次 30s 超时即抛错，无重试
- 瞬态故障（app-server 冷启动/负载抖动）被当终态处理

### 修复

**D32（协调者锁双信号存活判定，0.5.3）**：
- `observe()` 增 `holderAlive`（`pidAlive`，复用 procgroup）与 `hbSource`（token/owner-fallback/mtime）
- `steal()` 改 async 双信号：
  - **真崩溃（PID 已死）** → 立即抢锁（kill -9 接任 ≤5s SLA 不变）
  - **stalled-but-alive** → 记 `steal-deferred` 审计 + 宽限 3s 复核 + 15s 硬上限兜底
- 锁文件增 `startedAt` + `ps -o etime=` 防 PID 复用（macOS 无 `etimes`，用 `etime` 跨平台解析）
- 心跳首写失败补审计、renew 坏写重试一次才 markLost

**D33（provisioning 对账宽限，0.5.3）**：
- reconcile 按 journal 事件年龄（<60s）defer「记录缺失/首轮未受理」的瞬态判定
- 10s 后一次性 recheck（unref）
- 年龄超宽限或恢复抛错照旧定案（真故障不被掩盖）

### 验证

- unit-lock **16/16**（宽限不抢/hardExpiry 直抢/PID 复用/心跳重试）
- roster **36/36**（defer/超龄定案/抛错不 defer/无端口旧语义）
- 崩溃护栏 f29/crash-matrix/real-host **25/25**（takeover 实测 4270–4340ms ≤5s）
- 真会话 sess_cabd748c：建队期零误注入、切回套餐后 UPS 对账注入事实版提示且 Lead 一行说明+自干

### 残余面（登记不修）

- **Issue #11**：provisioning 瞬态失败无自动重试（failed 为终态，只能靠 Lead 手动换名重建）
- **Issue #12**：v4/command RPC 无幂等重试（超时即放弃，迟到的 anchor 会话可能泄漏到侧边栏）

## 五、问题 4：首次建队时冒出三个 MCP Daemon 页面

### 问题表现

首次新建成员时，ZCode 桌面冒出三个 MCP Daemon 页面（每个成员子会话一个）。

### 根因

`.mcp.json` 是**全局 MCP 配置**，宿主（ZCode）对**每个会话**都按它拉起一个 daemon 实例。成员子会话（`selection_side_chat`）也是会话 → 宿主给每个成员也拉一个 daemon。

**时间线取证**（sess_7b68447e）：
- 02:57:46 daemon 43832 启动（属于 Lead 会话）
- 02:57:49 daemon 43879 启动（属于 conceptor 子会话 `sess_e68631e7`）
- 02:57:49 daemon 43935 启动（属于**另一个**子会话 `sess_c3f0fde5`）

三个 daemon 实例**同时存在**，各自抢同一把 `coordinator.lock`。这就是 daemon-lifecycle 里 9 次 startup/exit 抖动的原因。

### 处理

**宿主行为改不了**，但 D32/D33 已经处理了锁竞争：
- D32 双信号判定：真崩溃（PID 已死）→ 立即抢锁（≤5s SLA 不变）；stalled-but-alive → 宽限复核
- D33 对账宽限：in-flight spawn 不再被误杀

**这是设计上的权衡**：daemon 多实例本身不是错（锁机制就是为了处理这个），错的是**锁被抢来抢去导致 provisioning 失败**。D32/D33 只缓解单项竞态；活持有者接任与迟到宿主结果的组合尚需保守唯一写者与持久恢复修复。

## 七、问题 6：团队协作业务模式奇怪

### 问题表现

`/team <任务>` 时先输出「成员 N · 共享任务 T」等状态摘要，再建队，体感奇怪。

### 根因

`/team` 命令的设计缺陷：带参时应该先建队执行，但规范写成「先输出状态摘要，再建队」。

### 修复

**b51ff30**：
- 无参 `/team` 仍输出摘要

- 补充 spawn 失败时的处理指引（provisioning 超时/RPC 超时时不要反复重试）

## 十一、0.5.4 修订与本轮验收

> 本节为后续修订；上方 0.5.3 的验收与发布记录保持历史事实。0.5.4 尚未提交/发布/安装。

- **发布边界修正**：`/team` 无参只读、带参直接执行；发布脚本要求显式冻结 commit SHA、同 SHA tag/远端基线，并校验命令文本及打包/解包一致。
- **保守唯一写者**：活持有者/存活未知不再因过期接任；确认退出仍 ≤5s。双进程 SIGSTOP/多竞争者/SIGCONT 门通过。
- **创建确认与恢复**：完整 origin 预写，固定 commandId、预分配 anchor 与进度证据；同进程/重启查询恢复原结果，unknown 不换号重建。
- **非终态与代次**：pending 保持 provisioning，原已确认 `{member}` 不变；失锁/探针/回执未知不进入 failed+interrupt；active 本地提交失败不反向杀成员。
- **启动/预算**：`starting` + `.spawn.json` + 转录确认，缺证据不重复启动；预算与截止时间持久化，跨接任不重置；停止自动恢复后不再误导 wait_agent 等待。
- **真实宿主探针**：隔离 HOME 验证同进程 duplicate、重启后 anchor query=unknown 但 session/list 可找回、child 原命令重启可恢复。
- **本轮实际验证**：全量 936/936；关键组合与真实失锁用例通过；S9 14 项、构建产物门与 `check` 通过。此前一次全量 935/936 的 SQLite locked 项单跑通过，复验完整套件通过，已如实记录。
